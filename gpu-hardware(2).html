Blackwell SM vs Hopper SM — Summary
Hopper: separate INT32 + FP32 pipes, 228 KB SMEM, registers hold accumulators. Blackwell: unified pipeline, 128 KB SMEM, but TMEM frees registers. CTA pairs double effective operand staging. 192 MB L2 (3.8×) compensates for smaller L1.

TC
ComputeMixed PrecisionArchitecture

Dedicated MMA hardware. 5th-gen adds FP4/FP6, tcgen05 single-thread async MMA (replacing wgmma), TMEM accumulation, and CTA-pair 2-SM cooperative MMA.

Operation D = A × B + C (MMA); D stored in TMEM on Blackwell H100 instr. wgmma — warp-group (128-thread), synchronous-ish B200 instr. tcgen05.mma (UMMA) — single-thread, fully async New Accumulator TMEM (Blackwell) vs registers (Hopper) — frees register file CTA Pair MMA 2 adjacent SMs cooperate on 1 MMA, shared TMEM region New NVFP4 Micro-block scaling: FP8 scale per 16 values + FP32 tensor scale New
2nd-Gen Transformer Engine (Blackwell)
Blackwell TE2 adds NVFP4 — two-level scaling (FP8 scale per 16 values + FP32 tensor scale). ≤1% accuracy loss vs FP8 while halving memory. TensorRT-LLM and NeMo apply automatically.

Register File
REG
MemoryOn-Chip

Fastest storage, private per-thread. On Blackwell, TMEM takes over accumulator duty — freeing registers for epilogue fusions and scheduling.

Bandwidth ~50+ TB/s effective Latency ~1 cycle Capacity 256 KB / SM Scope Private to each thread Spilling Overflow → local mem (L1→L2→HBM) — costly Limit 255 regs/thread max; exceeding reduces occupancy
Shared Memory / L1 Cache
SMEM
MemoryOn-Chip

Programmer-managed scratchpad within a block. Per-SM SMEM shrinks 228→128 KB on Blackwell, but CTA Pair MMA means each SM loads only half the operands — effective SMEM doubles.

BW (both) ~19 TB/s per SM Latency ~20–30 cycles H100 capacity 228 KB / SM (configurable L1 split) B200 capacity 128 KB / SM — reduced Blackwell Effective MMA CTA pair shares operands → each SM loads half → 256 KB effective Bank conflict 32 banks × 4 B; simultaneous same-bank access serialises Async copy TMA (H100+): HBM → SMEM without register staging
Tensor Memory (TMEM) New in Blackwell
TMEM
MemoryOn-ChipBlackwell-only

A new dedicated on-chip memory tier physically adjacent to Tensor Cores. Holds MMA accumulator results (matrix D), freeing the register file for epilogue and scheduling. Not present in any architecture before Blackwell.

Capacity 256 KB per SM — same size as register file Read BW 16 TB/s per SM — additive with SMEM Write BW 8 TB/s per SM Latency ~420 cycles Access model Lane-restricted; explicit alloc/dealloc Instructionstcgen05.cp · tcgen05.ld · tcgen05.st Operand rolesD (accumulator) always in TMEM. A from TMEM or SMEM. B from SMEM.
L2 Cache 4× bigger on Blackwell
L2
MemoryOn-Chip

Shared cache between all SMs and HBM. Blackwell dramatically expands L2 to 192 MB (3.8× H100's 50 MB) to compensate for smaller per-SM L1 and keep more LLM weight data on-chip during inference.

H100 50 MB · ~4 TB/s B200 192 MB · ~12 TB/s — 3.8× H100 Blackwell Latency ~100–200 cycles Scope All SMs share one unified L2 Residency cudaAccessPropertyPersisting: pin hot lines
HBM — High Bandwidth Memory
HBM
MemoryVRAM

Main GPU DRAM. All weights, activations, KV cache, optimizer state live here. Blackwell: 3.35→8 TB/s BW, 80→192 GB capacity. Primary bottleneck for memory-bound kernels.

H100 3.35 TB/s · 80 GB HBM3 B200 8 TB/s · 192 GB HBM3e — 2.4× BW, 2.4× cap Blackwell B300 Ultra ~10 TB/s · 288 GB HBM3e Ultra Latency ~700–1000 cycles Effective × NVFP4 + HW decompress → up to ~6× effective BW vs H100 FP16

NVS

Dedicated switch chips creating full all-to-all non-blocking NVLink fabric. Blackwell uses NVLink Switch sleds — separate rack units connecting GB200 server sleds into the NVL72 domain.

DGX H100 4× NVSwitch v3 chips · 3.6 TB/s bisection BW GB200 NVL72 NVLink Switch sleds — 130 TB/s full fabric Blackwell Topology Full all-to-all non-blocking — any GPU ↔ any GPU at full speed SHARP In-network aggregation: all-reduce executed inside switch chips (no GPU compute) Latency ~1 μs any-to-any within domain Form factor NVL72: server sleds + NVLink Switch sleds
PCIe & InfiniBand / RoCE
IB
InterconnectMulti-Node

Cross-node fabric. GB200 has a known RDMA latency issue (CX7 NIC traverses Grace NoC). GB300 Ultra fixes this with CX8 + external PCIe switch.

IB NDR 400 400 Gb/s · ~50 GB/s per port IB NDR 800 800 Gb/s · ~100 GB/s (Blackwell era clusters) vs NVLink 5 ~18× slower — TP cross-node is impractical GPUDirect RDMA GPU HBM ↔ NIC without CPU copy (same as H100) GB200 NIC CX7 — RDMA path traverses Grace NoC + C2C → added latency Known Issue GB300 NIC CX8 + external PCIe switch — direct RDMA path, latency fixed Ultra Fix
Cross-Node Parallelism Rules
PP (small P2P tensors) and DP (infrequent grad sync) tolerate IB. TP and EP must stay within the NVLink domain — NVL72 enables TP=72 within one rack.
NV-HBI — Dual-Die Interconnect Blackwell
HBI
ArchitectureBlackwell-only

Die-to-die interconnect connecting Blackwell's two reticle-limited dies into one logical GPU. Software sees a single address space; hardware maintains full cache coherence.

Why dual-die? Reticle limit ~850 mm² on TSMC 4NP; 208B transistors requires 2 dies Die config 2 dies × 74 SMs = 148 SMs; 4 L2 partitions/die; 8 HBM stacks/die NV-HBI BW ~10 TB/s coherent die-to-die vs HBM BW 10 TB/s HBI > 8 TB/s HBM — die boundary is not the bottleneck SW view Single CUDA device; no code changes required Process TSMC 4NP (4nm-class)

Roofline Model — H100 vs B200
ROOF
AnalysisBottleneck

Arithmetic intensity (FLOP/byte) determines compute-bound vs memory-bound. B200's FP4 ridge point is ~5000 FLOP/byte — nearly every LLM op is memory-bound at FP4.

Arith. Intensity FLOP ÷ HBM bytes accessed = which roof you hit Ridge Point H100 FP8~590 FLOP/B (1,979 TFLOPS ÷ 3.35 TB/s) Ridge Point B200 FP8~500 FLOP/B (4,000 TFLOPS ÷ 8 TB/s) — HBM BW improved more than FP8 compute Ridge Point B200 FP4~5,000 FLOP/B — nearly every LLM op is memory-bound at FP4!
