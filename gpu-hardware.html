Blackwell SM vs Hopper SM — Summary
Hopper: separate INT32 + FP32 pipes, 228 KB SMEM, registers hold accumulators. Blackwell: unified pipeline, 128 KB SMEM (smaller!), but TMEM takes accumulator duty freeing registers. CTA pairs effectively double operand staging. 192 MB L2 (3.8×) compensates for smaller L1.

2nd-Gen Transformer Engine (Blackwell)
Hopper TE: auto FP8/FP16 per layer. Blackwell TE2 adds NVFP4 — two-level scaling (FP8 micro-block scale per 16 values + FP32 tensor scale) achieves ≤1% accuracy vs FP8 while halving memory vs FP8 (~3.5× vs FP16). TensorRT-LLM and NeMo apply it automatically.

Register File
REG
MemoryOn-Chip

Fastest storage, private per-thread. On Blackwell, registers are freed from accumulator duty because TMEM takes over — allowing more registers for epilogue, activation fusions, and scheduling work.

Bandwidth ~50+ TB/s effective Latency ~1 cycle Capacity 256 KB / SM (65,536 × 32-bit) Scope Private to each thread Spilling Overflow → local mem (L1→L2→HBM) — very costly latency Limit 255 regs/thread max; exceeding reduces occupancy Blackwell Accumulator tiles removed → registers free for epilogue & pipelining
Tuning
Use __launch_bounds__ or maxrregcount to cap usage. On Blackwell, use CUTLASS 3.x — it manages TMEM allocation and minimizes register pressure automatically.

Tensor Memory (TMEM) New in Blackwell
TMEM
MemoryOn-ChipBlackwell-only

A new dedicated on-chip memory tier physically adjacent to Tensor Cores. Holds MMA accumulator results (matrix D), freeing the register file for epilogue and scheduling. Not present in any architecture before Blackwell.

Capacity 256 KB per SM — same size as register file Layout 512 columns × 128 lanes × 32-bit cells Read BW 16 TB/s per SM — additive with SMEM (not competing) Write BW 8 TB/s per SM Latency ~420 cycles — ~58% lower than Hopper's ~1000c register-spill path to L2/HBM Access model Lane-restricted; warpgroup must access collectively; explicit alloc/dealloc Instructionstcgen05.cp · tcgen05.ld · tcgen05.st Operand rolesMatrix D (accumulator) always in TMEM. A can come from TMEM or SMEM. B stays in SMEM.
Why TMEM Was Needed
Register pressureHopper: large accumulator tiles locked registers → reduced occupancy; register spills to L2/HBM
TC throughput gap5th-gen TCs so fast that SMEM+RF bandwidth couldn't keep them fed without TMEM
Epilogue overlapAccumulator in TMEM → epilogue ops (bias, activation) run in registers concurrently with next MMA
CTA pair sharingTwo SMs share TMEM region for 2-SM MMA — each SM only loads half the operands from SMEM
Programmer Impact
TMEM is programmer-managed (like SMEM). Use CUTLASS 3.x or ThunderKittens — they handle TMEM allocation. Raw CUDA: tcgen05.alloc / tcgen05.dealloc. Optimal tile: 64×64 FP8 (4 KB) to match 1024-bit TMEM interface width.
L2 Cache 4× bigger on Blackwell
L2
MemoryOn-Chip

Shared cache between all SMs and HBM. Blackwell dramatically expands L2 to 192 MB (3.8× H100's 50 MB) to compensate for smaller per-SM L1 and keep more LLM weight data on-chip during inference.

A100 40 MB · ~2 TB/s H100 50 MB · ~4 TB/s B200 192 MB · ~12 TB/s — 3.8× H100 Blackwell Latency ~100–200 cycles Scope All SMs; B200 has 8 L2 partitions (4/die × 2 dies) Residency cudaAccessPropertyPersisting: pin hot lines (H100+)
Impact for LLMs
192 MB L2 on B200 can cache full attention head projections and small KV blocks, dramatically reducing HBM round-trips. The 3.8× increase also compensates for smaller per-SM SMEM: data that used to need per-block staging now lives in L2 across all blocks.
HBM — High Bandwidth Memory
HBM
MemoryVRAM

Main GPU DRAM. All model weights, activations, KV cache, optimizer state live here. Blackwell doubles bandwidth (3.35→8 TB/s) and more than doubles capacity (80→192 GB). Primary bottleneck for memory-bound kernels.

NVLink 5th-gen on Blackwell
NVL
InterconnectMulti-GPUIntra-Node

Proprietary high-speed GPU-to-GPU interconnect. NVLink 5 (Blackwell) doubles to 1.8 TB/s per GPU. GB200 NVL72 creates a 72-GPU domain with 130 TB/s — up to 576 GPUs in one domain with >1 PB/s aggregate.

NVLink 4 (H100) 900 GB/s bidirectional per GPU NVLink 5 (B200) 1,800 GB/s bidirectional per GPU — 2× H100 Blackwell NVL72 total 130 TB/s across 72-GPU NVLink domain Max domain Up to 576 GPUs · >1 PB/s aggregate Multi-rack NVL NVLink-C2C 900 GB/s coherent CPU↔GPU (Grace Blackwell Superchip) vs PCIe 5 ~14× faster than PCIe 5 x16 Latency ~1 μs any-to-any within NVLink domain Enables TP all-reduce, SP, ZeRO-3 all-gather, EP all-to-all within domain
Why NVLink Confines TP to Intra-Node
TP all-reduce must complete in <1 ms to avoid stalling the forward pass. At 1.8 TB/s NVLink 5 vs 50 GB/s IB NDR, crossing node boundaries for TP is ~36× slower. This is a hard physical constraint — TP degree must always fit inside the NVLink domain.

PCIe & InfiniBand / RoCE
IB
InterconnectMulti-Node

Cross-node fabric. GB200 has a known RDMA latency issue (CX7 NIC traverses Grace NoC + NVLink-C2C). GB300 Ultra fixes this with CX8 + external PCIe switch, restoring low-latency RDMA paths.

PCIe 5 x16 128 GB/s bidirectional IB NDR 400 400 Gb/s · ~50 GB/s per port IB NDR 800 800 Gb/s · ~100 GB/s (Blackwell era clusters) vs NVLink 5 ~18× slower than NVLink 5 (NDR 400) — TP cross-node is impractical GPUDirect RDMA GPU HBM ↔ NIC without CPU copy (same as H100) GB200 NIC CX7 — RDMA path traverses Grace NoC + C2C → added latency Known Issue GB300 NIC CX8 + external PCIe switch — direct RDMA path, latency fixed Ultra Fix
Cross-Node Parallelism Rules
PP (small P2P activation tensors) and DP (infrequent grad sync) tolerate IB. TP and EP all-to-all at NVLink speeds would stall entirely over IB — they must stay within the NVLink domain. This is why NVL72 enables TP=72 within one rack.
NV-HBI — Dual-Die Interconnect Blackwell
HBI
ArchitectureBlackwell-only

NVIDIA High-Bandwidth Interface connecting Blackwell's two reticle-limited dies into one logical GPU. Software sees a single 192 GB address space; hardware uses NV-HBI for coherent, high-speed die-to-die traffic.

Why dual-die? Reticle limit ~850 mm² on TSMC 4NP; 208B transistors requires 2 dies Die config 2 dies × 74 SMs = 148 SMs; 4 L2 partitions/die; 8 HBM stacks/die NV-HBI BW ~10 TB/s coherent die-to-die vs HBM BW 10 TB/s HBI > 8 TB/s HBM — die boundary is not the bottleneck SW view Single CUDA device; no code changes required vs single-die Transistors 208B total — 2.6× Hopper's 80B Process TSMC 4NP (4nm-class)
vs AMD Multi-Chiplet (MCM)
Unlike AMD's external infinity fabric, NV-HBI maintains full cache coherence between dies at 10 TB/s — exceeding HBM bandwidth so inter-die traffic is never the bottleneck. CUDA programmers don't need to reason about die placement.

Hardware Decompression Engine New in Blackwell
DE
ArchitectureMemoryInference

Dedicated on-chip decompression hardware. Loads compressed model weights or KV cache from HBM and decompresses them on-chip at near-HBM bandwidth. No equivalent exists in any prior NVIDIA architecture.

Throughput Up to 539 GB/s decompression per GPU Latency <1 ms on 100 MB input blocks Formats LZ4 · Snappy · Zstandard · GZIP · Cascaded · Bitcomp · ANS Integration Transparent to CUDA kernels — decompression happens in the memory path Scaling Throughput varies with compression ratio and batch size

Compressed weightsStore model weights compressed in HBM; expand on-chip before GEMM — 2–3× effective BW
KV cacheCompressed KV cache in HBM → decompress before attention — key for long-context
DB queriesNVIDIA claims 18× speedup on DB joins vs CPU using HBM + DE (Snappy/Deflate)

Effective HBM Bandwidth Multiplier
At 3:1 LZ4 compression ratio, DE triples usable HBM BW for weight-loading: 8 TB/s → ~24 TB/s effective. Combined with NVFP4 (2× fewer bytes vs FP8), Blackwell can move ~6× more model data per HBM byte compared to H100 FP16.
RAS Engine New in Blackwell
RAS
ArchitectureReliabilityCluster-Scale

Dedicated Reliability, Availability, Serviceability hardware. Continuously monitors GPU health, predicts failures before they occur, and enables graceful degradation. Critical for week-long training runs on tens of thousands of GPUs.

Monitoring Continuous: thermals, power, SM errors, HBM ECC, NVLink status Predictive Early warning before hard failure → allows checkpoint + hot migration Degradation SM row remapping: retire faulty SM rows, continue running at slight perf reduction HBM ECC Single-bit correct + double-bit detect (same as H100) vs H100 H100 has ECC but no dedicated RAS Engine; monitoring was software-only (NVML)
Why RAS Matters at 10,000+ GPU Scale
A 10,000-GPU cluster expects multiple GPU failures per day. Without RAS, a hard failure kills the whole training job + loses time since last checkpoint. With RAS, the system predicts failure, checkpoints proactively, migrates the rank, replaces the node — training continues. Mean time between job kills goes from hours to days.

Grace CPU + NVLink-C2C
GRC
ArchitectureCPU+GPU

Arm Neoverse V2-based CPU paired with Blackwell via NVLink-C2C — a coherent 900 GB/s CPU-GPU link. Eliminates PCIe bottleneck; unified address space enables zero-copy GPU-CPU transfers.

Cores 72 × Arm Neoverse V2 cores L2 (GB200) 1 MB/core — reduced; higher L1 miss rate vs x86 Known issue L2 (GB300) 2 MB/core — standard; fixed in Ultra Fixed LPDDR5X 480 GB · 512 GB/s per Grace CPU NVLink-C2C 900 GB/s coherent CPU↔GPU — 7× faster than PCIe 5 Unified memory CPU + GPU share one address space — zero-copy buffer passing NVL72 total 36 CPUs × 480 GB = 17 TB LPDDR5X in one rack
LLM Use Cases Enabled by Grace
ZeRO-Infinity CPU offload at NVLink speed (not PCIe). Tokenisation/preprocessing on Grace, zero-copy transfer to B200. KV cache overflow to CPU DRAM at 900 GB/s vs ~64 GB/s PCIe 4. The 17 TB LPDDR5X on NVL72 is a massive pool for CPU-side KV offloading during very long-context (1M+ token) inference.
GB300 / B300 — Blackwell Ultra 2025
BLK-U
ArchitectureBlackwell Ultra

Successor to GB200/B200. Adds 160 SMs (+12), 288 GB HBM3e (+50%), 15 PFLOPS NVFP4 (+50%), and — critically — CX8 NIC with external PCIe switch that fixes the RDMA latency regression present in GB200.

SMs 160 SMs (+12 vs B200's 148) HBM3e 288 GB — +50% vs B200's 192 GB NVFP4 15 PFLOPS — 1.5× B200, 7.5× H100 FP8 5 PFLOPS — +11% vs B200 NVLink Same NVLink 5 — 1800 GB/s (no change) NIC CX8 + external PCIe switch — direct RDMA path, low latency Fixes GB200 Grace L2 Standard 2 MB/core (vs GB200's reduced 1 MB/core) Grace DRAM 480 GB LPDDR5X · 512 GB/s (same as GB200 configs) Power ~1.1–1.4 kW TDP per GPU (up from B200's 1.0 kW)
GB300 vs GB200 — What Actually Changed
GB200 had two known issues: (1) Grace L2 cache at 1 MB/core caused higher L1 miss rates vs x86 CPUs, hurting CPU-side preprocessing; (2) CX7 RDMA path traversed Grace NoC + NVLink-C2C, adding microseconds to cross-node collectives. GB300 fixes both. The NIC change is particularly important for large multi-node EP and DP workloads where collective latency matters.

Roofline Model — H100 vs B200
ROOF
AnalysisBottleneck

Arithmetic intensity (FLOP/byte) determines whether a kernel is compute-bound or memory-bound. B200's FP4 ridge point is at ~5000 FLOP/byte — nearly every LLM operation is memory-bound at FP4 precision.
