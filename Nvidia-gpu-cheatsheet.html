Compute Units
Streaming Multiprocessor (SM)
SM
ComputeArchitecture

The GPU's core compute unit. Each SM has CUDA cores for scalar math, Tensor Cores for matrix math, and on-chip memory (registers, SMEM, TMEM). Kernels are distributed across SMs by the GigaThread Engine.

Count 160 SMs · 80 per die (dual-die package) CUDA Cores 128 / SM — unified INT32+FP32 pipeline Blackwell Tensor Cores 4 / SM — matrix multiply-accumulate (MMA) units Registers 256 KB / SM — fastest storage, private per-thread SMEM + L1 228 KB / SM (B300/GB300, SM100) — 128 KB on consumer Blackwell (SM120). CTA Pairs give ~456 KB effective across 2 SMs TMEM 256 KB / SM — dedicated MMA accumulator store Blackwell Warps 64 warps/SM max (2048 threads) — GPU hides latency by switching warps
Tensor Cores 5th-gen Blackwell
TC
ComputeMixed Precision

Hardware units that perform matrix multiply-accumulate (D = A×B + C) in one clock. This is the core operation behind every transformer layer (attention QKV, FFN). All modern LLM training/inference throughput is TC-bound or HBM-bound.

What it does D = A × B + C — one fused matrix op per cycle per TC Formats FP16 · BF16 · TF32 · FP8 · FP4 · FP6 Blackwell MMA instr tcgen05 (UMMA) — 1 thread issues async MMA, accumulator in TMEM CTA Pair 2 SMs cooperate on 1 large MMA — doubles tile size New NVFP4 4-bit weights with micro-block scaling (FP8 per 16 vals) — ~1.8× less memory vs FP8, ~3.5× vs FP16 New
Transformer Engine v2 (Blackwell)
Auto-casts layers to optimal precision at runtime. TE2 adds NVFP4 with two-level scaling — ≤1% accuracy loss vs FP8 while halving memory. Applied automatically by TensorRT-LLM and NeMo.
Execution Model: Grid → Blocks → Warps → Threads
EXEC
ArchitectureCompute

CUDA programs launch a grid of thread blocks. Each block runs on one SM. Threads within a block are grouped into warps of 32 — the GPU's fundamental scheduling unit. When one warp stalls (e.g. memory load), another warp executes instantly — this is how GPUs hide latency. Warps map to CUDA cores for scalar ops (FP32/INT32). On Blackwell, Tensor Core MMA uses tcgen05 with single-thread semantics — one elected thread issues the async MMA instruction; operands live in SMEM and accumulators go directly to TMEM, freeing the register file entirely. (Hopper used wgmma which required a full warp group of 128 threads to cooperatively issue MMA.)

Grid All blocks for one kernel launch — distributed across all SMs by GigaThread Engine Cluster Group of blocks sharing distributed SMEM (DSMEM) across multiple SMs H100+ Block (CTA) Up to 1024 threads — shares SMEM + barriers — lives on 1 SM CTA Pair 2 adjacent blocks on 2 SMs cooperate — breaks the "1 block = 1 SM" rule; shares TMEM for one large MMA Blackwell Warp 32 threads executing in lockstep (SIMT) — zero-cost context switch on stall → dispatched to CUDA cores for scalar FP32/INT32 ops MMA dispatch Single-thread semantics on Blackwell (tcgen05) — one elected thread issues the async MMA; all other threads in the warp proceed independently. No warp-wide sync needed. Blackwell vs Hopper: wgmma required 128-thread warp group Thread Scalar unit with private registers — smallest execution unit
Perf Metric
Occupancy Warps resident on SM ÷ max (64). Sweet spot: 32–48 warps/SM. Too low = latency not hidden
Memory Hierarchy — Fastest → Slowest
Register File
REG
MemoryOn-Chip

Fastest memory on the GPU — 1 cycle access, private to each thread. Holds local variables and intermediate values. If a kernel uses too many registers, they "spill" to slow L1/L2/HBM, killing performance. On Blackwell, TMEM handles MMA accumulators so registers are freed for other work.

Bandwidth ~50+ TB/s effective Latency 1 cycle Size 256 KB / SM (65,536 × 32-bit registers) Scope Private per thread — not shared between threads Limit 255 regs/thread max — more regs per thread = fewer concurrent warps (lower occupancy) Spill Overflow goes to "local memory" which is actually L1→L2→HBM — 100–1000× slower
Shared Memory (SMEM) / L1 Cache
SMEM
MemoryOn-Chip

Fast on-chip scratchpad shared by all threads in a block. Used to stage data tiles loaded from HBM so both CUDA cores and Tensor Cores can access operands at high bandwidth without hitting slow DRAM. CUDA cores use SMEM for inter-thread communication, reductions, histograms, and any shared intermediate values; Tensor Cores use it to stage their A & B input tiles. L1 cache shares the same physical SRAM — the split is configurable at runtime.

Bandwidth ~19 TB/s per SM Latency ~20–30 cycles Size 228 KB / SM (B300/GB300, SM100) — CTA Pairs share across 2 SMs → ~456 KB effective. Note: consumer Blackwell (SM120) is 128 KB/SM Bank conflict32 banks × 4 B — if 2 threads hit same bank, access serializes (perf killer) TMA Tensor Memory Accelerator: async DMA from HBM→SMEM, no register staging H100+
Tensor Memory (TMEM) Blackwell Only
TMEM
MemoryOn-ChipBlackwell

New memory tier next to Tensor Cores, dedicated to holding MMA results (accumulator matrix D). Before Blackwell, accumulators lived in registers — consuming most of the register file and causing spills. TMEM eliminates this bottleneck: registers are freed for other work, and the next MMA can overlap with epilogue (bias, activation) in registers.

Size 256 KB / SM — same as register file Read BW 16 TB/s / SM — additive with SMEM (separate bus) Write BW 8 TB/s / SM Latency ~420 cycles (still on-chip, vs ~1000c for register spill to L2) What goes inD (accumulator) always in TMEM. A from TMEM or SMEM. B from SMEM. Access Programmer-managed: tcgen05.alloc / .ld / .st / .dealloc
L2 Cache 3.8× bigger on Blackwell
L2
MemoryOn-Chip

Hardware-managed cache shared by all SMs, sitting between on-chip memory and HBM. Every HBM access passes through L2 first. If the data is already cached, you save a ~700-cycle HBM round-trip. Blackwell's massive 192 MB L2 can hold full attention heads and small KV blocks on-chip.

Size 192 MB · ~12 TB/s Latency ~100–200 cycles (vs ~1 for regs, ~25 for SMEM, ~800 for HBM) Scope All SMs share one unified L2 — coherent across both dies via NV-HBI Hint API cudaAccessPropertyPersisting — tell L2 to keep specific data resident (hot weights)
HBM — High Bandwidth Memory (VRAM)
HBM
MemoryVRAM

The GPU's main DRAM — stacked memory chips on the package providing massive bandwidth via a wide bus (8192+ bits). All model weights, activations, KV cache, and optimizer states live here. Most LLM ops are HBM bandwidth-bound: compute finishes before the next data arrives.

Bandwidth 8 TB/s Capacity 288 GB HBM3e · 12 stacks (6 per die) Latency ~700–1000 cycles — this is why caching in L2/SMEM matters so much Effective BWNVFP4 (4× fewer bytes) + HW decompression (up to 3×) → up to ~24 TB/s effective

NVLink — GPU-to-GPU Interconnect v5 on Blackwell
NVL
InterconnectMulti-GPU

NVIDIA's proprietary high-speed link between GPUs (and CPU via C2C). Enables multi-GPU parallelism (tensor parallelism, expert parallelism) at low latency. TP and EP require NVLink-speed bandwidth — they cannot cross to InfiniBand without stalling.

NVLink 5 1,800 GB/s bidir per GPU Blackwell NVL72 fabric 130 TB/s total — 72 GPUs all-to-all via NVSwitch Max domain 576 GPUs · >1 PB/s aggregate (multi-rack NVLink) NVLink-C2C 900 GB/s coherent CPU↔GPU — replaces PCIe in Grace Blackwell Latency ~1 μs any-to-any within domain Used for TP all-reduce, EP all-to-all, ZeRO-3 all-gather, sequence parallelism
NVSwitch — NVLink Fabric Switch
NVS
InterconnectMulti-GPU

Dedicated switch chips that connect all GPUs in a full all-to-all non-blocking fabric. Without NVSwitch, GPUs would need point-to-point NVLinks (limiting topology). With it, any GPU can talk to any GPU at full speed. SHARP enables in-switch reduction — all-reduce without GPU compute.

NVL72 fabric NVLink Switch sleds — 130 TB/s full non-blocking fabric Topology Full all-to-all: any GPU ↔ any GPU at full NVLink speed SHARP In-network all-reduce — aggregation happens inside switch, zero GPU compute used Latency ~1 μs any-to-any within domain
InfiniBand / RoCE — Cross-Node Fabric
IB
InterconnectMulti-Node

Network fabric connecting GPU nodes across a cluster. ~18× slower than NVLink, so only pipeline parallelism (small tensors) and data parallelism (infrequent syncs) can cross node boundaries. TP and EP must stay within the NVLink domain.

NDR 800 ~100 GB/s per port vs NVLink ~18× slower — this is why TP can't cross nodes GPUDirect RDMA: GPU HBM ↔ NIC directly, no CPU copy needed GB200 issue CX7 NIC routes through Grace CPU → added RDMA latency Known Issue GB300 fix CX8 NIC + external PCIe switch → direct GPU-to-NIC path Fixed
NV-HBI — Die-to-Die Link Blackwell
HBI
ArchitectureBlackwell

Blackwell GPUs use two separate silicon dies (each ~850 mm², the max a single chip can be). NV-HBI is the on-package link that stitches them into one logical GPU. At 10 TB/s it's faster than HBM, so the die boundary is invisible to software — CUDA sees one device.

Why 2 dies Reticle limit: ~850 mm² max per die. 208B transistors needs 2 dies. Bandwidth ~10 TB/s coherent — faster than HBM (8 TB/s), so never the bottleneck Coherence Full L2 cache coherence across both dies Config 2 × 80 SMs = 160 SMs · 4 L2 partitions/die · 6 HBM stacks/die SW view Single CUDA device — no code changes needed vs single-die GPU

Decompression Engine (DE) Blackwell
DE
ArchitectureMemory

Hardware decompression unit that intercepts compressed data on the path from HBM to compute. Store model weights or KV cache compressed in VRAM → DE expands them on-the-fly at up to 539 GB/s. At 3:1 compression, effective HBM bandwidth triples (8 TB/s → ~24 TB/s). Combined with NVFP4, this means Blackwell moves far more model data per byte than older FP16 workflows.

Throughput Up to 539 GB/s per GPU Formats LZ4 · Snappy · Zstandard · GZIP · ANS How it worksTransparent — sits in memory path, CUDA kernels don't need changes Key use Compressed weights in HBM → expand on-chip before GEMM (2–3× effective BW)
RAS Engine — Reliability Blackwell
RAS
ArchitectureReliability

Dedicated hardware for Reliability, Availability, Serviceability. At 10K+ GPU scale, multiple GPUs fail daily. RAS continuously monitors health, predicts failures before they happen, and enables the system to checkpoint and migrate jobs — keeping training alive without manual intervention.

Monitors Thermals, power, SM errors, HBM ECC, NVLink status — always on Predictive Warns before hard failure → proactive checkpoint + hot migration Self-heal SM row remapping: retires faulty SM rows, GPU keeps running at ~99% perf
Superchip & Node — Grace CPU + GPU Package
Grace CPU + NVLink-C2C
GRC
ArchitectureCPU+GPU

Arm-based CPU on the same superchip as the GPU, connected via NVLink-C2C (900 GB/s) instead of PCIe. This means CPU↔GPU transfers run at 7× PCIe speed with a unified address space — enabling efficient KV cache overflow to CPU DRAM and ZeRO-Infinity offloading at NVLink bandwidth.

Cores 72 × Arm Neoverse V2 L2 cache 2 MB/core GB300 fix from GB200's 1 MB/core DRAM 480 GB LPDDR5X · 512 GB/s per CPU C2C link 900 GB/s coherent CPU↔GPU — 7× PCIe 5 NVL72 pool 36 CPUs × 480 GB = 17 TB CPU DRAM per rack
B300 / GB300 — Blackwell Ultra 2025
BLK-U
ArchitectureBlackwell Ultra

The "fixed and upgraded" version of B200/GB200. More SMs, 50% more VRAM, 50% more FP4 compute. Most importantly, it fixes two GB200 pain points: the CPU L2 cache was too small (hurting preprocessing), and the RDMA path added latency because the NIC routed through the CPU.

SMs 160 (+12 vs B200's 148) HBM3e 288 GB — +50% vs B200 (192 GB) NVFP4 15 PFLOPS — 1.5× B200 NIC fix CX8 + external PCIe switch → direct GPU-to-NIC RDMA path Key Fix CPU L2 fix 2 MB/core (vs GB200's under-provisioned 1 MB/core) Key Fix Power ~1.1–1.4 kW TDP per GPU
Rack-Scale Systems — NVL72
NVL72 — Rack-Scale GPU System Blackwell
NVL72
ArchitectureSystemMulti-GPU

An NVL72 is one liquid-cooled rack containing 36 Grace Blackwell Superchips — each superchip has 1 Grace CPU + 2 GPUs — giving 72 GPUs and 36 CPUs total. All 72 GPUs are connected via NVLink 5 through NVLink Switch sleds, forming a single flat, all-to-all fabric with no hops. From any GPU's perspective, all other 71 GPUs are reachable at full NVLink speed (~1 μs). This makes the entire rack behave like one giant GPU for tensor parallelism, expert parallelism, and ZeRO-3.

GPUs per rack 72 × Blackwell GPUs (2 per superchip × 36 superchips) CPUs per rack 36 × Grace CPUs — each connected to 2 GPUs via NVLink-C2C Total HBM 20.7 TB HBM3e (GB300 NVL72) Total CPU DRAM 17 TB LPDDR5X (36 × 480 GB) NVLink fabric 130 TB/s any-to-any — all 72 GPUs non-blocking via NVLink Switch sleds Latency ~1 μs any GPU → any GPU within the rack Cross-node IB / RoCE to other racks — ~18× slower than NVLink; TP & EP must stay within NVL72 Key use Large model training and inference — TP/EP/SP within rack, PP & DP across racks
Why it matters for parallelism
Tensor parallelism and expert parallelism require very frequent all-reduce / all-to-all collectives. At NVLink speeds (130 TB/s fabric) these are cheap. Crossing to InfiniBand between racks is ~18× slower, so TP degree is limited to what fits within the NVL72 domain. Pipeline parallelism (small point-to-point activations) and data parallelism (infrequent gradient sync) are the only strategies that can span racks efficiently.

Roofline Model — Am I Compute-Bound or Memory-Bound?
ROOF
AnalysisBottleneck

The roofline tells you which ceiling your kernel hits. Divide FLOP by bytes loaded from HBM = arithmetic intensity (AI). If AI < ridge point, you're memory-bound (waiting for data). If AI > ridge point, you're compute-bound (math units are the limit). At FP4 precision, the ridge point is so high (~5000) that almost every LLM operation is memory-bound.

Formula AI = FLOP ÷ bytes loaded from HBM. Below ridge → memory-bound. Above → compute-bound. Ridge point AI = compute TFLOPS ÷ HBM BW. Most LLM ops fall well below — they're memory-bound.
