Compute Units
Streaming Multiprocessor (SM)
SM
ComputeArchitecture

The GPU's core compute unit. Each SM has CUDA cores for scalar math, Tensor Cores for matrix math, and on-chip memory (registers, SMEM, TMEM). Kernels are distributed across SMs by the GigaThread Engine.

Count 108 (A100) · 132 (H100) · 148 (B200) · 160 (B300) CUDA Cores 128 / SM — unified INT32+FP32 pipeline Blackwell Tensor Cores 4 / SM — matrix multiply-accumulate (MMA) units Registers 256 KB / SM — fastest storage, private per-thread SMEM + L1 228 KB (H100) → 128 KB (B200) — smaller, but CTA Pairs compensate TMEM 256 KB / SM — dedicated MMA accumulator store Blackwell Warps 64 warps/SM max (2048 threads) — GPU hides latency by switching warps
Blackwell vs Hopper SM
Hopper: separate INT/FP pipes, 228 KB SMEM, accumulators in registers. Blackwell: unified pipe, 128 KB SMEM, TMEM holds accumulators freeing registers. CTA Pairs let 2 SMs share work → effective 256 KB SMEM. 192 MB L2 (3.8×) compensates for smaller per-SM cache.
Tensor Cores 5th-gen Blackwell
TC
ComputeMixed Precision

Hardware units that perform matrix multiply-accumulate (D = A×B + C) in one clock. This is the core operation behind every transformer layer (attention QKV, FFN). All modern LLM training/inference throughput is TC-bound or HBM-bound.

What it does D = A × B + C — one fused matrix op per cycle per TC Formats FP16 · BF16 · TF32 · FP8 · FP4 · FP6 Blackwell H100 MMA wgmma — 128 threads cooperate, accumulator in registers B200 MMA tcgen05 (UMMA) — 1 thread issues async MMA, accumulator in TMEM New CTA Pair 2 SMs cooperate on 1 large MMA — doubles tile size New NVFP4 4-bit weights with micro-block scaling (FP8 per 16 vals) — halves memory vs FP8 New
Transformer Engine v2 (Blackwell)
Auto-casts layers to optimal precision at runtime. TE2 adds NVFP4 with two-level scaling — ≤1% accuracy loss vs FP8 while halving memory. Applied automatically by TensorRT-LLM and NeMo.
Execution Model: Threads → Warps → Blocks
EXEC
ArchitectureCompute

CUDA programs launch a grid of thread blocks. Each block runs on one SM. Threads within a block are grouped into warps of 32 — the GPU's fundamental scheduling unit. When one warp stalls (e.g. memory load), another warp executes instantly — this is how GPUs hide latency.

Thread Scalar unit with private registers — smallest execution unit Warp 32 threads executing in lockstep (SIMT) — zero-cost context switch on stall Block (CTA) Up to 1024 threads — shares SMEM + barriers — lives on 1 SM Grid All blocks for one kernel launch, distributed across all SMs CTA Pair 2 blocks on 2 adjacent SMs share TMEM for one large MMA Blackwell Cluster Group of blocks sharing distributed SMEM (DSMEM) across SMs H100+ Occupancy Warps resident on SM ÷ max (64). Sweet spot: 32–48 warps/SM. Too low = latency not hidden
Memory Hierarchy — Fastest → Slowest
Register File
REG
MemoryOn-Chip

Fastest memory on the GPU — 1 cycle access, private to each thread. Holds local variables and intermediate values. If a kernel uses too many registers, they "spill" to slow L1/L2/HBM, killing performance. On Blackwell, TMEM handles MMA accumulators so registers are freed for other work.

Bandwidth ~50+ TB/s effective Latency 1 cycle Size 256 KB / SM (65,536 × 32-bit registers) Scope Private per thread — not shared between threads Limit 255 regs/thread max — more regs per thread = fewer concurrent warps (lower occupancy) Spill Overflow goes to "local memory" which is actually L1→L2→HBM — 100–1000× slower
Shared Memory (SMEM) / L1 Cache
SMEM
MemoryOn-Chip

Fast on-chip scratchpad shared by all threads in a block. Used to stage data tiles loaded from HBM so Tensor Cores can access them at high bandwidth instead of going to slow DRAM every time. L1 cache shares the same physical SRAM — the split is configurable at runtime.

Bandwidth ~19 TB/s per SM Latency ~20–30 cycles H100 size 228 KB / SM (configurable L1/SMEM split) B200 size 128 KB / SM — smaller, but CTA Pairs share across 2 SMs → 256 KB effective Bank conflict32 banks × 4 B — if 2 threads hit same bank, access serializes (perf killer) TMA Tensor Memory Accelerator: async DMA from HBM→SMEM, no register staging H100+
Tensor Memory (TMEM) Blackwell Only
TMEM
MemoryOn-ChipBlackwell

New memory tier next to Tensor Cores, dedicated to holding MMA results (accumulator matrix D). Before Blackwell, accumulators lived in registers — consuming most of the register file and causing spills. TMEM eliminates this bottleneck: registers are freed for other work, and the next MMA can overlap with epilogue (bias, activation) in registers.

Size 256 KB / SM — same as register file Read BW 16 TB/s / SM — additive with SMEM (separate bus) Write BW 8 TB/s / SM Latency ~420 cycles (still on-chip, vs ~1000c for register spill to L2) What goes inD (accumulator) always in TMEM. A from TMEM or SMEM. B from SMEM. Access Programmer-managed: tcgen05.alloc / .ld / .st / .dealloc
L2 Cache 3.8× bigger on Blackwell
L2
MemoryOn-Chip

Hardware-managed cache shared by all SMs, sitting between on-chip memory and HBM. Every HBM access passes through L2 first. If the data is already cached, you save a ~700-cycle HBM round-trip. Blackwell's massive 192 MB L2 can hold full attention heads and small KV blocks on-chip.

H100 50 MB · ~4 TB/s B200 192 MB · ~12 TB/s — 3.8× larger, 3× faster Blackwell Latency ~100–200 cycles (vs ~1 for regs, ~25 for SMEM, ~800 for HBM) Scope All SMs share one unified L2 — coherent across both dies via NV-HBI Hint API cudaAccessPropertyPersisting — tell L2 to keep specific data resident (hot weights)
HBM — High Bandwidth Memory (VRAM)
HBM
MemoryVRAM

The GPU's main DRAM — stacked memory chips on the package providing massive bandwidth via a wide bus (8192+ bits). All model weights, activations, KV cache, and optimizer states live here. Most LLM ops are HBM bandwidth-bound: compute finishes before the next data arrives.

H100 3.35 TB/s · 80 GB HBM3 B200 8 TB/s · 192 GB HBM3e — 2.4× BW, 2.4× capacity Blackwell B300 ~10 TB/s · 288 GB HBM3e Ultra Latency ~700–1000 cycles — this is why caching in L2/SMEM matters so much Effective BWNVFP4 (4× fewer bytes) + HW decompression (3×) → up to ~6× vs H100 FP16

NVLink — GPU-to-GPU Interconnect v5 on Blackwell
NVL
InterconnectMulti-GPU

NVIDIA's proprietary high-speed link between GPUs (and CPU via C2C). Enables multi-GPU parallelism (tensor parallelism, expert parallelism) at low latency. TP and EP require NVLink-speed bandwidth — they cannot cross to InfiniBand without stalling.

NVLink 4 900 GB/s bidir per GPU (H100) NVLink 5 1,800 GB/s bidir per GPU — 2× H100 Blackwell NVL72 fabric 130 TB/s total — 72 GPUs all-to-all via NVSwitch Max domain 576 GPUs · >1 PB/s aggregate (multi-rack NVLink) NVLink-C2C 900 GB/s coherent CPU↔GPU — replaces PCIe in Grace Blackwell Latency ~1 μs any-to-any within domain Used for TP all-reduce, EP all-to-all, ZeRO-3 all-gather, sequence parallelism
NVSwitch — NVLink Fabric Switch
NVS
InterconnectMulti-GPU

Dedicated switch chips that connect all GPUs in a full all-to-all non-blocking fabric. Without NVSwitch, GPUs would need point-to-point NVLinks (limiting topology). With it, any GPU can talk to any GPU at full speed. SHARP enables in-switch reduction — all-reduce without GPU compute.

DGX H100 4× NVSwitch v3 chips · 3.6 TB/s bisection BW NVL72 NVLink Switch sleds — 130 TB/s full non-blocking fabric Blackwell Topology Full all-to-all: any GPU ↔ any GPU at full NVLink speed SHARP In-network all-reduce — aggregation happens inside switch, zero GPU compute used Latency ~1 μs any-to-any within domain
InfiniBand / RoCE — Cross-Node Fabric
IB
InterconnectMulti-Node

Network fabric connecting GPU nodes across a cluster. ~18× slower than NVLink, so only pipeline parallelism (small tensors) and data parallelism (infrequent syncs) can cross node boundaries. TP and EP must stay within the NVLink domain.

NDR 400 ~50 GB/s per port NDR 800 ~100 GB/s per port (Blackwell-era clusters) vs NVLink ~18× slower — this is why TP can't cross nodes GPUDirect RDMA: GPU HBM ↔ NIC directly, no CPU copy needed GB200 issue CX7 NIC routes through Grace CPU → added RDMA latency Known Issue GB300 fix CX8 NIC + external PCIe switch → direct GPU-to-NIC path Fixed
NV-HBI — Die-to-Die Link Blackwell
HBI
ArchitectureBlackwell

Blackwell GPUs use two separate silicon dies (each ~850 mm², the max a single chip can be). NV-HBI is the on-package link that stitches them into one logical GPU. At 10 TB/s it's faster than HBM, so the die boundary is invisible to software — CUDA sees one device.

Why 2 dies Reticle limit: ~850 mm² max per die. 208B transistors needs 2 dies. Bandwidth ~10 TB/s coherent — faster than HBM (8 TB/s), so never the bottleneck Coherence Full L2 cache coherence across both dies Config 2 × 74 SMs = 148 SMs · 4 L2 partitions/die · 6 HBM stacks/die SW view Single CUDA device — no code changes needed vs single-die GPU

Per-GPU Silicon — New Blackwell Engines
Decompression Engine (DE) Blackwell
DE
ArchitectureMemory

Hardware decompression unit that intercepts compressed data on the path from HBM to compute. Store model weights or KV cache compressed in VRAM → DE expands them on-the-fly at up to 539 GB/s. At 3:1 compression, effective HBM bandwidth triples (8 TB/s → ~24 TB/s). Combined with NVFP4, Blackwell moves ~6× more model data per byte than H100 FP16.

Throughput Up to 539 GB/s per GPU Formats LZ4 · Snappy · Zstandard · GZIP · ANS How it worksTransparent — sits in memory path, CUDA kernels don't need changes Key use Compressed weights in HBM → expand on-chip before GEMM (2–3× effective BW)
RAS Engine — Reliability Blackwell
RAS
ArchitectureReliability

Dedicated hardware for Reliability, Availability, Serviceability. At 10K+ GPU scale, multiple GPUs fail daily. RAS continuously monitors health, predicts failures before they happen, and enables the system to checkpoint and migrate jobs — keeping training alive. H100 relied on software monitoring only.

Monitors Thermals, power, SM errors, HBM ECC, NVLink status — always on Predictive Warns before hard failure → proactive checkpoint + hot migration Self-heal SM row remapping: retires faulty SM rows, GPU keeps running at ~99% perf
Superchip & Node — Grace CPU + GPU Package
Grace CPU + NVLink-C2C
GRC
ArchitectureCPU+GPU

Arm-based CPU on the same superchip as the GPU, connected via NVLink-C2C (900 GB/s) instead of PCIe. This means CPU↔GPU transfers run at 7× PCIe speed with a unified address space — enabling efficient KV cache overflow to CPU DRAM and ZeRO-Infinity offloading at NVLink bandwidth.

Cores 72 × Arm Neoverse V2 L2 cache 1 MB/core (GB200) → 2 MB/core (GB300) — GB200 was under-provisioned DRAM 480 GB LPDDR5X · 512 GB/s per CPU C2C link 900 GB/s coherent CPU↔GPU — 7× PCIe 5 NVL72 pool 36 CPUs × 480 GB = 17 TB CPU DRAM per rack
B300 / GB300 — Blackwell Ultra 2025
BLK-U
ArchitectureBlackwell Ultra

The "fixed and upgraded" version of B200/GB200. More SMs, 50% more VRAM, 50% more FP4 compute. Most importantly, it fixes two GB200 pain points: the CPU L2 cache was too small (hurting preprocessing), and the RDMA path added latency because the NIC routed through the CPU.

SMs 160 (+12 vs B200's 148) HBM3e 288 GB — +50% vs B200 (192 GB) NVFP4 15 PFLOPS — 1.5× B200 NIC fix CX8 + external PCIe switch → direct GPU-to-NIC RDMA path Key Fix CPU L2 fix 2 MB/core (vs GB200's under-provisioned 1 MB/core) Key Fix Power ~1.1–1.4 kW TDP per GPU

Roofline Model — Am I Compute-Bound or Memory-Bound?
ROOF
AnalysisBottleneck

The roofline tells you which ceiling your kernel hits. Divide FLOP by bytes loaded from HBM = arithmetic intensity (AI). If AI < ridge point, you're memory-bound (waiting for data). If AI > ridge point, you're compute-bound (math units are the limit). At FP4 precision, the ridge point is so high (~5000) that almost every LLM operation is memory-bound.

Formula AI = FLOP ÷ bytes loaded from HBM. Below ridge → memory-bound. Above → compute-bound. H200 FP8 ridge ~412 FLOP/B (1,979 TFLOPS ÷ 4.8 TB/s) B300 FP8 ridge ~450 FLOP/B (~4,500 TFLOPS ÷ ~10 TB/s) B300 FP4 ridge ~6,000 FLOP/B (60,000 TFLOPS ÷ ~10 TB/s) — nearly every LLM op is memory-bound at FP4
