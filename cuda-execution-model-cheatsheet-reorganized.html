1. Core execution hierarchy
CUDA hierarchy from kernel launch to lane
HIER
gridblockwarpthread
Most CUDA tuning decisions are about how your work maps onto this hierarchy and how that mapping interacts with SM resources.
GRID
Grid = all blocks in one kernel launch
Blocks are independent by default; they may run in any order on any SM.
BLOCK
Thread Block (CTA) = cooperative group on one SM
Shares shared memory and can use __syncthreads(). Max 1024 threads/block.
WARP
Warp = 32 threads (SIMT scheduling unit)
Warp scheduler issues instructions for warps; divergence serializes paths.
THREAD
Thread = one logical lane
Own registers, private local memory (spills), scalar code view.
1D global idx
gid = blockIdx.x * blockDim.x + threadIdx.x
Warp id
warpId = threadIdx.x >> 5 (within block)
Lane id
laneId = threadIdx.x & 31
Warp size
Always 32 (do not hardcode assumptions beyond that constant, use warpSize)
Thread dims
threadIdx.{x,y,z}, blockIdx.{x,y,z}, blockDim.{x,y,z}, gridDim.{x,y,z}
Organization rule of thumb: First choose a block shape that matches your data tile / memory layout; then check occupancy, divergence, and coalescing.
Built-in indices and common mappings
ID
1D2D3D
1D array

2D matrix
row = blockIdx.y*blockDim.y + threadIdx.y
col = blockIdx.x*blockDim.x + threadIdx.x
3D volume
Add z = blockIdx.z*blockDim.z + threadIdx.z

Bounds guard
if (i < N) ... or if (row < H && col < W)
Tail warps (partial final warp) are normal. They reduce lane utilization but are usually fine if they only occur at boundaries.
SIMT vs SIMD mental model
SIMT
warpdivergence
  • SIMT: Threads are programmed independently, but execution is grouped by warp. (CUDA abstraction)
  • SIMD-like issue: A warp usually executes one instruction across active lanes. (hardware behavior)
  • Divergence: If lanes take different branches, paths execute serially with masks.
  • Predication: Very short conditionals may compile to predicated instructions (no explicit branch).
  • Volta+: Independent Thread Scheduling improves safety/flexibility, but warp-level assumptions still require explicit masks and sync where needed.

Memory ordering essentials
FENCE
atomicsvisibility
  • Barrier (like __syncthreads()) provides both execution sync and shared-memory visibility within a block.
  • Atomics serialize updates to one address, but they are not a full-block barrier.
  • Fences (__threadfence_block, __threadfence, __threadfence_system) order writes across scopes.
  • For producer→consumer across blocks, combine correct ordering + signaling (often atomics) + kernel boundary or cooperative sync.
3. Warp execution, divergence, and scheduling
Warp scheduler behavior (high level)
WARP
eligiblestalls
Scheduling unit
Warp (32 threads)
Goal
Issue from an eligible warp while others wait on dependencies
Hidden latency
Memory, long ALU ops, pipeline dependencies
Needs
Enough active warps and/or enough ILP to keep execution units busy
Practical tuning: occupancy helps only if the added warps are actually eligible (not all stalled on the same bottleneck).
Divergence cost model
DIV
branchingpredication
Best case
Warp-uniform branch → no divergence penalty
Common case
Two paths in a warp → roughly serialized into two masked passes
Worst case
Path per lane → severe throughput collapse
Avoid by
Mapping data so branch conditions align with warp boundaries; split kernels when branch behavior differs widely
Okay when
Boundary checks only affect a few warps or rare conditions
Coalescing and warp memory access
MEM
global memorycoalescing
  • Global memory is most efficient when adjacent lanes access adjacent addresses.
  • Strided or scattered accesses increase memory transactions and reduce throughput.
  • Map threadIdx.x to the fastest-varying data dimension whenever possible.
  • For matrices, row/column choice should match your storage layout and reuse strategy.
  • Use shared memory tiling when direct global accesses are uncoalesced or repeatedly reused.
4. Block/SM resources and occupancy
Occupancy limits — what actually caps resident warps
OCC
registersshared memorywarpsblocks
Occupancy = active warps / maximum warps on an SM. It is a capacity metric, not a direct performance metric.
LimiterHow it caps occupancySymptomTypical fix
Warp slotsHard architectural cap (e.g., up to 64 resident warps/SM on many recent NVIDIA GPUs)Can't exceed max occupancy even with tiny kernelsNone (hardware limit)
Threads / block shapeSmall blocks may hit max blocks/SM before max warps/SMExample: 32-thread blocks often top out at ~50% warp occupancyUse 128–256 threads/block unless algorithm dictates otherwise
Registers / threadMore live values → fewer resident warps/blocksptxas -v shows high register usage or spillsReduce live ranges, tune unroll, __launch_bounds__, maybe --maxrregcount
Shared memory / blockBig tiles reduce resident blocksOnly 1–2 blocks/SMShrink tile or split stages; use async copies / pipelining
Block count capSM can host only up to a fixed number of blocksTiny blocks underfill warpsIncrease block size
Healthy default: Start with blockDim = 128 or 256. Then profile. Compute-bound kernels may run best well below 100% occupancy if ILP is strong.
Shared memory & bank conflicts
SMEM
bankspadding
Banks
32 banks (bank mapping depends on access width / architecture mode)
Conflict-free
Lanes hit different banks, or same address (broadcast)
Conflict
Different addresses in same bank → serialized access
Classic fix
Padding: float tile[32][33] to avoid stride-32 conflicts
Dynamic smem
extern __shared__ T smem[]; and pass bytes in launch config
Use Nsight Compute shared-memory conflict metrics to confirm. Padding is a common fix, not a universal one.
Occupancy and ILP tradeoff
ILP
unrollregister pressure
  • Higher ILP helps a warp make progress while waiting on dependent instructions.
  • But ILP usually increases register usage, which can lower occupancy.
  • This tradeoff is normal: many fast kernels choose moderate occupancy + strong ILP.
  • Use #pragma unroll selectively and verify with profiling.
  • If spills appear, back off unrolling or restructure temporaries.

Cooperative launch and clusters (advanced)
ADV

  • Cooperative launch enables grid-wide synchronization via cooperative groups.
  • Thread block clusters (Hopper+) add a larger execution/sync scope than a single block.
  • Cluster features are architecture-specific and come with placement constraints.
  • Use them only when the algorithm truly benefits from cross-block cooperation.
6. Common limits and gotchas
Hardware / programming limits checklist
LIMITS
max threadsgrid dimsregisters
LimitTypical value / rule
Warp size32 threads
Threads per block≤ 1024
blockDim.zMuch smaller than x/y max; respect per-dimension limits
Registers per threadHard cap exists; high usage lowers occupancy and may spill
Shared memory per blockLimited and architecture-dependent; dynamic SMEM may need opt-in attributes
Grid dimensionsPer-dimension limits differ (x is much larger than y/z)
  • Incorrect barrier placement is a top source of hangs.
  • 100% occupancy is not the goal; throughput is.
  • Small blocks can underutilize SMs due to max-blocks/SM cap.
  • Big blocks can hurt tail handling and reduce residency.
  • Spills often erase gains from aggressive unrolling.
  • Divergence at boundaries is usually acceptable; divergence in the hot interior is expensive.
Keep this order: correctness → coalescing → block shape → occupancy/regs → unrolling/ILP → micro-optimizations.
